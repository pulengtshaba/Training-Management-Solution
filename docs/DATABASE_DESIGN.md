# Training Management System

## Database Design Document

Version: 1.0

Database Engine: Microsoft SQL Server

ORM: Entity Framework Core

---

# 1. Purpose

This document describes the logical database design for the Training Management System (TMS).

The database is designed to support employee training management while maintaining data integrity, scalability, and performance.

---

# 2. Design Principles

The database has been designed using the following principles:

* Data normalization (up to Third Normal Form where appropriate)
* Referential integrity
* Minimal data duplication
* Clear naming conventions
* Indexed search columns
* Auditability
* Future scalability

# 4. Core Tables

## Branch

Represents a physical business location.

| Column   | Type          | Description        |
| -------- | ------------- | ------------------ |
| BranchId | INT           | Primary Key        |
| Name     | NVARCHAR(100) | Branch name        |
| Code     | NVARCHAR(20)  | Unique branch code |
| Address  | NVARCHAR(250) | Branch address     |
| IsActive | BIT           | Active status      |

Relationships:

* One Branch has many Employees.
* One Branch has many Venues.

---

## Employee

Stores employee information.

| Column         | Type          |
| -------------- | ------------- |
| EmployeeId     | INT           |
| EmployeeNumber | NVARCHAR(30)  |
| FirstName      | NVARCHAR(100) |
| LastName       | NVARCHAR(100) |
| Email          | NVARCHAR(255) |
| PhoneNumber    | NVARCHAR(20)  |
| BranchId       | INT           |
| RoleId         | INT           |
| IsActive       | BIT           |

Relationships:

* Belongs to one Branch.
* Has one Role.
* Can register for many Training Sessions.
* Can have many Attendance records.

---

## Role

Defines system permissions.

Examples:

* Administrator
* Manager
* Trainer
* Employee

| Column | Type         |
| ------ | ------------ |
| RoleId | INT          |
| Name   | NVARCHAR(50) |

---

## TrainingProgram

Represents a reusable training course.

Examples:

* Health & Safety
* Customer Service
* First Aid

| Column        | Type          |
| ------------- | ------------- |
| ProgramId     | INT           |
| Title         | NVARCHAR(200) |
| Description   | NVARCHAR(MAX) |
| DurationHours | INT           |
| IsActive      | BIT           |

One programme can have many Training Sessions.

---

## Venue

Represents a training location.

| Column   | Type          |
| -------- | ------------- |
| VenueId  | INT           |
| BranchId | INT           |
| Name     | NVARCHAR(150) |
| Capacity | INT           |

---

## TrainingSession

Represents a scheduled occurrence of a programme.

| Column          | Type         |
| --------------- | ------------ |
| SessionId       | INT          |
| ProgramId       | INT          |
| VenueId         | INT          |
| TrainerId       | INT          |
| StartDate       | DATETIME2    |
| EndDate         | DATETIME2    |
| MaximumCapacity | INT          |
| Status          | NVARCHAR(30) |

---

## Registration

Represents an employee's enrolment in a training session.

| Column           | Type         |
| ---------------- | ------------ |
| RegistrationId   | INT          |
| EmployeeId       | INT          |
| SessionId        | INT          |
| RegistrationDate | DATETIME2    |
| Status           | NVARCHAR(30) |

Business Rule:

An employee may only register once for the same session.

A unique constraint should enforce:

(EmployeeId, SessionId)

---

## Attendance

Stores attendance outcomes.

| Column         | Type         |
| -------------- | ------------ |
| AttendanceId   | INT          |
| RegistrationId | INT          |
| CheckInTime    | DATETIME2    |
| CheckOutTime   | DATETIME2    |
| Status         | NVARCHAR(30) |

Possible statuses:

* Pending
* Attended
* Missed
* Cancelled

---

## Notification

Stores notifications generated by the system.

| Column           | Type          |
| ---------------- | ------------- |
| NotificationId   | INT           |
| Title            | NVARCHAR(200) |
| Message          | NVARCHAR(MAX) |
| CreatedDate      | DATETIME2     |
| NotificationType | NVARCHAR(50)  |

---

## NotificationRecipient

Supports notifications sent to multiple users.

| Column                  | Type      |
| ----------------------- | --------- |
| NotificationRecipientId | INT       |
| NotificationId          | INT       |
| EmployeeId              | INT       |
| IsRead                  | BIT       |
| ReadDate                | DATETIME2 |

# 5. Relationships

Summary of key relationships:

* Branch → Employees (1:N)
* Branch → Venues (1:N)
* TrainingProgram → TrainingSessions (1:N)
* Venue → TrainingSessions (1:N)
* Employee → Registrations (1:N)
* TrainingSession → Registrations (1:N)
* Registration → Attendance (1:1)
* Notification → NotificationRecipients (1:N)

---

# 6. Naming Conventions

Tables:

* Singular names (Employee, Branch, Venue)

Primary Keys:

* EntityNameId

Examples:

* EmployeeId
* SessionId
* VenueId

Foreign Keys:

* Reference the related entity.

Examples:

* BranchId
* ProgramId
* TrainerId

---

# 7. Indexing Strategy

Indexes should be created on columns frequently used for searching, filtering, sorting, or joining.

Recommended indexes:

* EmployeeNumber (Unique)
* Email (Unique)
* BranchId
* ProgramId
* TrainerId
* SessionId
* RegistrationDate
* StartDate
* Status

Composite indexes:

* (EmployeeId, SessionId)
* (BranchId, StartDate)

Indexes should be reviewed as query patterns evolve.

---

# 8. Constraints

Examples:

* Employee email must be unique.
* Employee number must be unique.
* Session capacity must be greater than zero.
* Registration must reference an existing employee.
* Attendance cannot exist without a registration.
* Training session end date must be after the start date.

---

# 9. Auditing

The following entities should support auditing:

* Employee
* TrainingProgram
* TrainingSession
* Registration
* Attendance

Suggested audit columns:

* CreatedDate
* CreatedBy
* ModifiedDate
* ModifiedBy

Optional future enhancement:

Maintain a separate AuditLog table for recording significant system events.

---

# 10. Performance Considerations

To support large datasets:

* Use pagination for list endpoints.
* Project only required columns.
* Use AsNoTracking() for read-only queries.
* Avoid N+1 query patterns.
* Create indexes based on measured query performance.
* Archive historical data if required by business needs.

---

# 11. Future Database Enhancements

Potential future additions include:

* Certificate
* FileAttachment
* AuditLog
* RefreshToken
* BackgroundJob
* OutboxMessage
* SystemSettings

These tables can be introduced without significant changes to the existing schema.

---

# 12. Summary

The database design emphasizes:

* Data integrity through foreign keys and constraints.
* Performance through appropriate indexing.
* Maintainability through consistent naming conventions.
* Scalability for future enhancements.

The schema supports the current business requirements while allowing the system to evolve as new features are introduced.
